## What to build

Integrate and reproduce the capabilities and evidence delivered by the earlier slices. A portfolio reviewer can start the local Docker Compose product, run the real 20-character CLI experience and inspect credible comparisons of conventional, graph, investigative and automatically routed answers. This is the acceptance run of an existing suite, not the first ticket that adds tests or evaluations.

## Acceptance criteria

- [ ] Demonstrate fresh local setup with Python/LlamaIndex, FastAPI, PostgreSQL/pgvector, Prefect and MLflow, documented provider/configuration choices and conservative limits. Exercise actual three-route answers, automatic selection and visible overrides/fallbacks, follow-ups, clarification, partial/abstain outcomes and reset.
- [ ] Run the confirmed public-boundary unit/integration suite using real storage and controlled external services, plus separately budgeted live-provider checks. Associate software-test artifacts and MLflow component/end-to-end reports with the evaluated source/code revision.
- [ ] After baseline measurement and before examining held-out candidate comparisons, record the selected numerical thresholds, k values, case counts/repeats and limit settings. Freeze reference artifacts/splits, snapshot, answer-model settings, prompts, tool contracts and scorers; keep held-out labels out of tuning.
- [ ] Compare always-text, graph-capable, investigative and routed policies on the same corpus/questions. Use eligible-route counterfactuals and targeted ablations, paired per-case changes, category breakdowns, sample sizes and suitable uncertainty estimates. Repeated stochastic runs are not independent questions.
- [ ] Inspect final persona answers and actual evidence appendices as well as component outcomes. Reviewed demonstration cases and deterministic contracts pass; resolve critical factual, biological/guilt, citation and answerability failures rather than averaging them away. Report judge configuration/calibration and its limitations.
- [ ] Report complete serving latency/cost including routing, checking and retries, with offline evaluation expenditure separate and missing usage explicit. Verify manual refresh, interrupted-operation recovery and return to a compatible prior code/prompt/data configuration.
- [ ] Publish a local run/recovery procedure, coverage/known-limitations report and linked evidence register. Assign the project owner acceptance and future hosting/refresh decisions; record feedback-to-regression and dependency-change recheck rules. R Shiny, production hosting and weekly deployed operations remain outside this release.
- [ ] Demonstrate optional feedback for actual text, graph and investigative responses, including a follow-up and a partial/abstain/clarification outcome. Verify original response/trace/snapshot association, durable receipt, duplicate/revised input and session/reset behavior through the CLI/API.
- [ ] With the normal local stack running, show that feedback and sampled served traces automatically produce online metrics/assessments and a review disposition. Include late feedback after initial assessment, unrated sampling, unavailable/failed judges and exhausted evaluation budget without blocking chat. A manual offline run alone does not pass.
- [ ] Inspect feedback coverage and every metric denominator, cohort/version and selection policy; keep satisfaction, reported errors, automated quality and reviewed correctness separate. Verify a checked feedback case enters a versioned regression dataset without held-out leakage. Label demo traffic as test data and show online expense separately from serving/offline costs.
- [ ] Record applicable checklist results and revision-linked evidence in the project register, including failures, limitations and follow-up regressions. A documented plan alone does not pass an implementation check.
